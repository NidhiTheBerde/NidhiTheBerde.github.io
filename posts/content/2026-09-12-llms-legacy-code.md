A lot of the AI coding hype right now is demoed on greenfield projects: a clean prompt, a fresh repo, a model that writes idiomatic code because idiomatic code is most of what it was trained on. The story gets a lot messier the moment you point the same model at a twenty-year-old codebase that's been touched by forty different engineers, half of whom have since left the company. I wanted to actually understand why, instead of just accepting "legacy code is hard" as a given.

## The problem

**The training data is skewed toward what's popular now, not what's actually running in production.** Public code on GitHub massively overrepresents modern, well-formatted, idiomatic code in mainstream languages. It massively underrepresents COBOL, old VB6, ancient Perl, undocumented internal DSLs, and the specific dialect of enterprise Java that was considered best practice in 2008. A model can be extremely fluent in Python and still be shaky on the actual language a bank's core ledger system runs on.

**Context windows don't fix missing context.** Even a huge context window only helps if the information the model needs is written down somewhere it can read. Legacy systems are full of implicit knowledge that was never documented: why a particular check exists, what edge case a weird conditional is actually guarding against, which of three similar-looking functions is the one that's actually still called in production. A bigger window lets you feed in more code, but it can't retrieve context that only exists in a retired employee's memory.

**The code encodes decades of undocumented business rules.** A block that looks like dead weight to a model reading it cold might be silently compensating for a bug in a mainframe compiler from 1995, or encoding a regulatory requirement that's never written down anywhere near the code itself. An LLM has no way to distinguish "this can be safely deleted" from "this one weird line is the only thing preventing a compliance violation," because both look like ordinary code.

**Side effects and coupling are often invisible in the file you're looking at.** Legacy systems lean heavily on global state, shared mutable data, and cross-service side effects that don't show up when you're staring at one function. A model reasoning locally about a single file can miss that changing it breaks three other systems that read from the same table under assumptions nobody wrote down.

**There's usually no safety net.** Modern codebases at least tend to have some test coverage you can use to check whether a change broke something. A lot of legacy systems have thin or no automated tests, which means there's no fast, cheap way to verify that a model's suggested change actually preserves behavior. That absence matters more here than almost anywhere else, because the code that's hardest to test is often also the code that's riskiest to get wrong.

**And the stakes are asymmetric.** The systems most likely to be old, undocumented, and full of implicit business logic are also disproportionately the ones running banking, insurance, healthcare, and government infrastructure. A hallucinated explanation of a greenfield React component is annoying. A hallucinated explanation of what a COBOL batch job actually does before someone modifies it is a different category of risk entirely.

## What people are actually doing about it

The realistic approaches I've seen fall into a few buckets.

**Purpose-built models instead of general-purpose ones.** Rather than relying on a general model's shaky exposure to COBOL, some efforts train or fine-tune specifically on mainframe languages. XMainframe is one example, a model built specifically around mainframe and COBOL knowledge rather than treating it as an afterthought in a general pretraining mix. IBM's watsonx Code Assistant for Z takes a similar purpose-built approach for COBOL, PL/I, and JCL, and has published claims around roughly 80% code accuracy on COBOL-to-Java conversion, which is meaningfully better than what you'd expect from pointing a generalist model at the same problem cold.

**Multi-agent pipelines instead of a single prompt.** Microsoft's approach to COBOL migration uses multiple coordinating agents, one for analysis, one for conversion, one for dependency mapping, rather than asking a single model call to understand and rewrite a system in one shot. Splitting "understand what this does" from "map how it connects to everything else" from "generate the replacement" mirrors how a careful human engineer would actually approach the same migration, and it gives you more places to sanity-check the output along the way.

**Retrieval and dependency mapping instead of raw context stuffing.** Rather than dumping as much code as fits into a context window, tools increasingly build an actual structural map of the codebase first, call graphs, dependency graphs, cross-references, and retrieve the specific relevant pieces for a given task. This is a much better fit for legacy systems than naive retrieval, because the thing that trips people up usually isn't the code you're looking at, it's the code somewhere else that depends on it.

**Human-in-the-loop by default, not as an afterthought.** Given how asymmetric the risk is, the more serious tools treat human review as a core part of the workflow rather than an optional safety net bolted on afterward, especially anywhere near regulated or financial systems.

The honest state of the field right now: Gartner has warned that a large majority of mainframe migrations attempted this year are on track to fail, largely because organizations are overestimating what generative AI alone can do here. At the same time, there are real, large-scale wins, Morgan Stanley has reportedly modernized over 17 million lines of COBOL, Natural, and Perl using an in-house generative AI platform. Both of those things are true at once. This isn't a solved problem, and the gap between the demo and the messy 20-year-old production system is exactly where most of the real engineering work still has to happen.
